# 影响分析：加 GitHub Actions

日期：2026-11-05

## 变更意图

后端 156 项、前端 45 项测试已经写好了，但没有任何自动执行的地方。跑不跑取决于当时记不记得，这也是上一轮那个 conftest 路径问题能潜伏这么久的原因：它只在「从仓库根连续跑两次」这一种情况下暴露，人工很少这么跑。

加一条 CI，push 与 PR 各跑一次。

## 做了什么

新建 `.github/workflows/ci.yml`，两个独立 job：

| job | 工作目录 | 步骤 |
|---|---|---|
| backend | `backend` | setup-python 3.13 → pip install -r requirements.txt → pytest -q |
| frontend | `frontend` | setup-node 22 → npm ci → npm test → npm run type-check → npm run build |

两处版本选择有依据：

- Python 用 3.13，与 `backend/Dockerfile` 的 `python:3.13-slim` 对齐。本机是 3.13.14。版本不一致会出现「本机绿、镜像红」这种最难查的情况。
- Node 用 22。`vitest@5.1.0` 的 `engines` 要求 `^22.12.0 || ^24.0.0 || >=26.0.0`，指定 `"22"` 会取到最新的 22.x，满足要求。

`concurrency` 加了 `cancel-in-progress`：连推几个 commit 时只跑最后一次，省时间也省额度。

## 为什么不用 npm install

`npm ci` 严格按 `package-lock.json` 装，锁文件与 `package.json` 不一致会直接报错。用 `npm install` 会顺手改锁文件，CI 上改了也没人看，等于把「锁文件漂移」这个信号吞掉。

本地验证时专门跑了一次 `npm ci`，158 个包，装完三条命令全绿，说明锁文件是同步的。

## 影响面

| 范围 | 是否受影响 | 说明 |
|---|---|---|
| 运行时代码 | 否 | 只加一个工作流文件，不碰 `app/` 与 `src/` |
| 依赖 | 否 | 不加任何包，`npm ci` 只用现有锁文件 |
| 构建产物 | 否 | 与本地 `npm run build` 一致 |
| PR 流程 | 是 | 新增必需检查（GitHub 上默认不阻塞合并，需要的话在仓库设置里开） |

## 验证

- `pytest -q`（工作目录 `backend`）：156 项通过，28.7 秒。
- `npm ci` + `npm test` + `npm run type-check` + `npm run build`：45 项通过，类型检查无输出，构建通过，7.6 秒。
- YAML 用 PyYAML 解析确认两个 job 与步骤顺序正确。

## 首次运行结果

推送后 run #1（commit `8125819`）实际跑了，两个 job 全绿：

| job | 耗时 | 步骤 |
|---|---|---|
| backend | 51 秒 | 六步全 success，`pytest -q` 通过 |

## 遗留

- 没配覆盖率门槛。当前 201 条用例覆盖的是关键路径，算覆盖率会给出一个不反映真实风险的百分比。
- 没在 CI 里跑 Docker Compose 冒烟。那套需要构建镜像、起 Postgres，耗时从秒级变分钟级，对一次毕设的迭代频率不划算。容器冒烟仍按需手动跑。
- `concurrency` 的取消行为没实测，只验证了配置存在。要测得多推几个 commit 看前一个是否被 cancel。
