# 2026-11-06 侧边栏高度与导出/下载链路修复

## 侧边栏高度各页面不一致

`AppLayout` 的 `aside` 没有独立高度约束，靠父容器 `flex` 的 `stretch` 拉到与右侧内容等高。首页内容长时 aside 高 1422px，评估页 1953px，底部主题/退出按钮跟着内容跑，长页面里首屏根本看不到。

给 aside 加 `lg:sticky lg:top-6 lg:h-[calc(100vh-3rem)] lg:self-start`，固定为视口高度、滚动时保持可见。实测首页与评估页 aside 高度都变成 516px（视口 1000 - 上下各 24 - 内边距），top 都是 24，完全一致。浅色/深色与移动端（抽屉）不受影响。

## 报告导出 PDF 三处缺陷

`ReportDetailView.printPdf` 上一版是「fetch → window.open → document.write → addEventListener('load') → print」。三个问题：

1. `document.write` + `close()` 是同步的，文档 `load` 事件早触发过了，之后再 `addEventListener('load', ...)` 永远收不到，`win.print()` 不执行，用户只得到一个静态 HTML 页。改成写完 `setTimeout(() => win.print(), 300)`。
2. `window.open` 放在 `await fetch` 之后，脱离了用户手势的同步调用栈，浏览器弹窗拦截器会挡下。改成同步栈里先开窗拿引用，再 fetch 填充；失败时 `win.close()` 关掉空窗。
3. `download()` 里 `URL.revokeObjectURL` 紧跟 `link.click()` 同步释放，Firefox 下下载队列还没取走 blob；且 `a` 没 append 进文档，Firefox 不触发下载。

## 下载逻辑抽成共用工具

`ProfileView.downloadFile` 与 `ReportDetailView.download` 是两份一模一样的代码，且都带上面第 3 点的缺陷。抽 `utils/download.ts::downloadBlob(blob, filename)`：`appendChild` → `click` → `remove` → 延迟 1 秒 `revokeObjectURL`。

测试 `utils/download.spec.ts` 4 条，覆盖挂文档、文件名与 href、revoke 不同步、一秒后释放。注意别用 `vi.stubGlobal('URL', ...)`：happy-dom 点 a 标签时内部要 `new URL()` 导航，把构造函数换成普通对象会炸出一片 TypeError 还假绿；改用 `vi.spyOn(URL, 'createObjectURL')` 只替换静态方法。

变异两处都咬住：去掉 `appendChild` → 「点击时链接仍在文档里」挂；把延迟 revoke 改成同步 → 「revoke 不同步调用」挂。

## 多序列趋势图改为共享日期轴

11-05 那版 `buildMultiChart` 让各序列按自己的点数独立铺满横轴。点数不等时这就是错的：收缩压测了 11-01/02/03、舒张压只测了 11-02/03，舒张压的 11-02 会被画在画布最左端，和收缩压的 11-02 差了半张图。用户想看的恰恰是「同一天两条线是不是一起动」。

改成共享日期轴：

- 几何层把所有序列的测量日期取并集、排序（归一到 `YYYY-MM-DD`，与横轴刻度 `MM-DD` 同粒度），每个点按自己那天在轴上的位置取 x，不再按序号铺满。`MultiChartLayout` 多带一个 `dates` 字段。
- 缺测日期**不补点、不插值**：只有相邻两个实测点之间连一条线，横向距离反映真实日期差。之前把「对齐」等同于「时间桶化 + 插值」是判断过头，按天定位不需要插值。
- 同一天测了多次就共用一个 x 垂直叠着画，不擅自挑一条；后端返回顺序也不再被假设为升序，几何层自己按 `measured_at` 排。
- 横轴刻度改从共享日期轴生成，不再取「点数最多的序列」——那条序列可能恰好漏了中间几天。全为无效值的序列被过滤在日期并集之前，不会凭空把轴拉长。
- `ChartPointLayout` 加 `date` 字段（单序列 `buildChart` 也一并填），组件据此把悬停那天的所有序列值列进提示框；没测的指标不列。同一天的点跨序列一起放大，视觉上能看出对齐。

页面文案同步改成「横轴按测量日期对齐，同一天的测量落在同一条竖线上；没测的日期不补点」。

测试：几何层 6 → 12 条（新增并集对齐、首条序列最稀疏、缺测空档、乱序排序、同日多次测量、零间距段不产生 NaN、共享轴刻度；旧「各自铺满」断言已按新语义改写），组件层 6 → 10 条（新增 SVG `cx` 对齐、同日多指标提示、缺测不列、跨序列高亮）。前端 182 → 192 项。

## 真 Postgres 上补完 checkpointer 断点一致性验证

Docker 恢复后，用 `AsyncPostgresSaver` 连真库构造带 `interrupt()` 的最小图，先把事实测清楚（Windows 下 psycopg/asyncpg 要 `SelectorEventLoop`，用 `asyncio.Runner(loop_factory=...)`）：

1. 跑到 interrupt 时 `checkpoints` 表落库，`aget_state().next == ('confirm',)`。
2. `_fail` 只写 `workflow_runs.status = failed`，**不碰 checkpointer**：DB 说失败，图仍停在「等你确认」。
3. 同一 `conversation.thread_id` 再发一条新消息，`astream` 会从 `START` 重跑并覆盖断点（真库实测 `nodes=['collect','__interrupt__']`）。
4. 对已 failed 的 run 调 `Command(resume=...)` 照样能继续执行到 finished —— 旧 run 就这么被复活了。

根因是**粒度不对齐**：checkpointer 按会话（`thread_id`）只存一份断点，而 `workflow_runs` 是按 run 一行。用户在待确认时又发一条新消息，会留下一个孤儿 `waiting_user` run；旧确认卡片若还能点，`resume_run` 会把新一轮的断点接回旧 run，并把旧 run 改回 `running`。而 `ChatView.send()` 原本**不**清 `confirmation`，卡片确实还留在页面上。另外 `resume_run` 遇到不存在的 run 是裸 `return`，前端只收到一条空 SSE 流，转圈停了却什么都没说。

修复：

- `chat_repo.expire_pending_runs()`：新一轮开始前，把同会话仍为 `waiting_user` 的旧 run 收成 `cancelled` 并写 `completed_at`。只动 `waiting_user`，`running` 那条可能真在跑，收口交给它自己的 `_finish/_fail`。
- `graph_service.resume_run()`：状态不是 `waiting_user` 一律拒绝，出 `run_error` / `RUN_NOT_RESUMABLE`；找不到 run 出 `RUN_NOT_FOUND`；plan approve 缺版本 id 也不再静默返回，出同一类错误。守卫不改状态，`failed` 留作审计。
- `ChatView`：`send()` 清掉旧确认卡片；`handleEvent` 收到 `run_error` 也清掉，避免过期卡片被反复点。

验证分两层：

- 离线回归 `tests/regression/test_resume_guard.py` 6 条（新消息作废旧卡片、不存在 run 报错、failed run 不复活且不改状态、正常 waiting_user 仍可恢复、作废只限同一会话、plan 缺 id 报错），sqlite + InMemorySaver，CI 无需起 Postgres。前端 `ChatView.spec.ts` 补 2 条（发新消息清卡片、modify 分支下 run_error 清卡片）。五轮变异分别挂 2/2/1/1/1 条。
- 真库端到端：另建 `ah_verify` 库，`CHECKPOINTER=postgres` 起完整 app（ASGI 进程内，不占用端口），走注册→画像→发消息→确认卡片→再发一条→点旧卡片。实测 `checkpointer ready backend=postgres`、中断时 `checkpoints` 6 行、`expired pending runs count=1`、旧 run 变 `cancelled`、旧卡片返回 `RUN_NOT_RESUMABLE`、不存在的 run 返回 `RUN_NOT_FOUND`。验证库随后 `DROP DATABASE ... WITH (FORCE)` 清掉。

残留取舍：`cancelled` 只写业务表，不清 checkpointer 里的旧断点（真库收尾时该 thread 仍从 6 行涨到 11 行）；新一轮从 `START` 重跑会覆盖它，但重叠的流之间仍有窗口。前端主动 abort 后后端那条 `running` run 依旧可能悬挂（老问题，不在这次范围内）：`start_run` 只收 `waiting_user`，没动 `running`，避免误伤真在执行的流。要做成「取消即终态」得让 `_finish/_fail/_mark_waiting` 都尊重 `cancelled`，那是另一轮改动。
